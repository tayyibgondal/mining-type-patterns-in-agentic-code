\subsection{Stage 2: Multi-agent LLM-based Pipeline}
\label{sec:stage2}

Stage~1 is tuned for recall, so the set it produces still contains PRs that match a construct pattern without performing any construct-related work. Two cases account for most of them. The first is under-described PRs. Many PRs, and Agentic PRs in particular, carry short or generic prose, so a PR titled ``Fix bugs'' may rewrite a trait hierarchy without ever using the word ``type''. The second is incidental matches, where a PR mentions ``type'' or contains a generic instantiation only in a line that was touched as a side effect of an unrelated change. Neither case can be settled by a regular expression, because both require reading a diff as a change with an intent rather than as a set of tokens. Stage~2 therefore replaces pattern matching with semantic judgement.

\subsubsection{Architecture}

The stage is organised as a two-agent chain: a classifier agent that makes the decision, and a validator agent that reviews it. We use a separate validator rather than a single agent with a longer prompt because the two roles have different objectives. The classifier is asked to detect evidence, while the validator is asked to be sceptical of the classifier's own reasoning. These are different tasks, and the second one catches over-confident positives that self-review inside a single call does not.

The classifier agent receives the PR title, the description, the commit messages, the code patches, and change statistics covering lines added, lines deleted, and the number of modified source files of the target language. The prompt supplies a language-specific operational definition of what counts as a construct-related change, stated as a list of concrete edit kinds rather than as an abstract criterion. For Rust, the definition covers changes to type annotations and signatures, changes to lifetimes and lifetime elision, changes to generics, trait bounds, \texttt{where} clauses, \texttt{impl Trait} and \texttt{dyn Trait}, the addition or refactoring of traits, type aliases and associated types, changes that affect borrow-checker or ownership behaviour, the replacement of \texttt{.unwrap()} or \texttt{.expect()} with explicit \texttt{Option} and \texttt{Result} handling and the reverse, the introduction or removal of \texttt{unsafe} blocks, functions, traits and impls, the migration of \texttt{as} casts to fallible conversions such as \texttt{TryFrom}, newtype and \texttt{PhantomData} wrapping, smart-pointer wrapping, \texttt{Send} and \texttt{Sync} fixes, and the repair of compile-time type errors. The TypeScript and C\# prompts are structurally identical and differ only in this definition, which is instantiated from the same feature set used by the corresponding Stage~1 parser, so that both stages answer the same question about the same constructs.

The classifier returns a single JSON object containing a boolean decision, a confidence score in $[0,1]$, a written rationale, a list of discrete evidence items quoted from the input, and a record of which input channel each piece of evidence was found in, namely the title, the description, the commit messages, or the patches. Requiring the evidence list and the channel breakdown serves two purposes. It forces the decision to be grounded in the supplied text rather than in a prior about what PRs usually do, and it makes the stage auditable, since every accepted PR carries the specific lines that caused it to be accepted. The prompt also instructs the agent to classify positively only when the evidence is clear, which biases this stage towards precision. That is the complement of the Stage~1 bias, and it is the reason the two stages compose into a funnel instead of duplicating each other.

The validator agent receives a condensed view of the PR, consisting of the title, the description, and the file and line counts, together with the classifier's decision, confidence and rationale. It is prompted as a senior reviewer of the target language and asked four questions: whether the stated rationale is supported by the evidence, whether the decision is a false positive, whether it is a false negative, and whether the reported confidence is appropriate given the strength of the evidence. It returns a verdict of \texttt{APPROVED}, \texttt{REJECTED} or \texttt{UNCERTAIN}, its own confidence, its reasoning, and any suggested correction. The validator does not re-read the diff, since its role is to audit the justification rather than to re-derive the decision. This is what makes it an independent check rather than a second, correlated classifier.

Acceptance is conjunctive. Writing $\mathit{Cls}(p)$ for the classifier's boolean decision on PR $p$, and $\mathit{Val}(p)$ for the event that the validator returns \texttt{APPROVED}, the final dataset is

\[
\mathit{Accept}(p) \;=\; \mathit{Retain}(p) \;\wedge\; \mathit{Cls}(p) \;\wedge\; \mathit{Val}(p),
\]

where $\mathit{Retain}(p)$ is the Stage~1 predicate defined in the previous section. An \texttt{UNCERTAIN} verdict is therefore treated as a rejection. A PR wrongly admitted at this point contaminates every downstream measurement, whereas the corpus is large enough to absorb the loss of a genuinely borderline PR, so we resolve ambiguity against inclusion here. This is the opposite of the trade-off we made in Stage~1. For every PR we persist both verdicts together with their confidences and rationales, so that any later result can be traced back to the judgement that admitted the PR.

Both agents run at a low sampling temperature and are constrained to emit machine-parseable JSON, so that their decisions are close to deterministic and can be logged without post-hoc text parsing. PRs are processed in batches with a bounded number of concurrent requests and a per-request timeout. Every call is wrapped so that a timeout, an API error, or an unparseable response yields a negative result rather than an exception. The pipeline therefore fails closed, which means that transport-level failures can only cost us PRs and can never introduce spurious ones. Such failures were negligible in practice, for example a single failed call out of 1{,}579 in the agentic Rust run.

The stage is markedly selective. In the agentic runs it accepted 648 of the 1{,}083 TypeScript PRs retained by Stage~1 (59.8\%), 709 of 1{,}392 for C\# (50.9\%), and 290 of 790 for Rust (36.7\%). The human runs were more selective still. The validator accounted for a non-trivial share of these rejections, overturning 103 of the 1{,}083 agentic TypeScript classifications and 94 of the 195 human C\# classifications, which confirms that the second agent is not redundant with the first. Table~\ref{tab:dataset_size} reports the number of PRs surviving each stage.

\subsubsection{Validation}

We evaluate Stage~2 with the same consensus protocol used for Stage~1, but on the population that Stage~2 actually operates on, namely the PRs retained by Stage~1. For each language we drew a stratified sample of 50 PRs from that population, 25 that the pipeline accepted and 25 that it rejected, under a fixed random seed. Two researchers with substantial experience in the language independently labelled each PR for whether it genuinely contains construct-related changes, without access to the pipeline's verdict or rationale. The annotators then cross-checked their labels and resolved every disagreement through discussion until consensus was reached. Treating a PR that genuinely contains construct-related changes as the positive class, we computed the confusion matrix of the pipeline's decision against this consensus label and derived accuracy, precision, recall, specificity and F1-score. Table~\ref{tab:filtering_performance} reports the results.

Two caveats govern how these figures should be read. First, they are conditional on Stage~1 having retained the PR. This is the correct denominator for judging Stage~2 in isolation, but it means that the Stage~1 and Stage~2 columns of Table~\ref{tab:filtering_performance} describe different populations, so they cannot be compared directly and cannot be multiplied to obtain an end-to-end figure. Second, because the sample is stratified into equal halves rather than drawn in proportion to the pipeline's actual acceptance rate, the reported accuracy and specificity are properties of the balanced sample and not estimates of the corresponding population quantities. Precision and recall are computed within a single predicted or actual class and are therefore unaffected by the stratification. Unlike Stage~1, we weight precision most heavily here, because Stage~2 is the last filter in the pipeline and any false positive it admits enters the analysed corpus unchecked.
